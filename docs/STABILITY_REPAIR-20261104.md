# 2026-11-04：QQ 崩溃及启动恢复

## 根因与现场

07:41 重启后，Windows 事件中没有新增 0x50 蓝屏；C 盘新增 256 MB 分页文件已实际启用。本次 QQ 故障是应用启动问题。

- QQ 弹窗为 0x80000003，位置 0x00007FFA845E6E3A。NapCat 启动日志停在注入后，JS/WebUI 未初始化，桥持续离线。
- 定时巡逻任务一直在执行，返回码为 0，但旧恢复条件只看进程是否存在；崩溃弹窗让 QQ/引导器残留，因此没有恢复。
- NapCat 安装目录及引导器继承了 Low 完整性标签。管理员只读查询证明，引导器和它的两个 QQ 进程均为 Low（RID 4096），即使计划任务设置为 Highest。
- 对应上游同症状记录 [NapCatQQ #2116](https://github.com/NapNeko/NapCatQQ/issues/2116)。微软明确说明新进程会受可执行文件完整性级别限制：[Mandatory Integrity Control](https://learn.microsoft.com/en-us/windows/win32/secauthz/mandatory-integrity-control)。

## 本机验证与修复

只将 `NapCatWinBootMain.exe` 的完整性标签恢复为 Medium。引导器 SHA-256 与访问权限 DACL 前后均不变；未换 QQ、NapCat 或 hook 版本。结束范围仅为本安装目录引导器及其 QQ 子进程，未停止 DSH 或调试器。

14:15 重新启动后，引导器和 QQ 主进程为 Medium（RID 8192），OneBot 连接恢复；QQ 的沙盒子进程仍可正常处于 Low，这不属于故障。以上前后对比确认了本次启动故障的原因。

代码修复：

- `start_all.ps1` 在已有最高权限任务中，对生产引导器做相同的一处完整性标签检查/修正，防止更新后重新继承 Low；普通调用转交现有高权限任务。
- 已连接时跳过重复启动；启动宽限期内保留进程；WebUI 已启动时保留扫码/登录状态。只有确认桥离线、启动超时且 WebUI 尚未初始化时，才恢复本引导器的 QQ 进程树。
- 巡逻狗识别“进程还在但初始化已失败”的状态；每小时恢复最多 3 次，保留冷却期。单轮任务仍不触发 DSH 强杀。QQ 断线时检查结果显示 warn，不再显示整体健康。
- 两个任务的运行程序由应用执行别名改为系统自带 Windows PowerShell 完整路径，避免开机别名执行失败。对应脚本保持 UTF-8 BOM，并验证 PowerShell 5.1 兼容。
- QQ 空间桥此前任务结果为 0x80074001；恢复启动后，5700 的已鉴权只读检查通过。其 CMD 启动改为显式 cmd.exe，未就绪时返回非零；原有本地鉴权值迁入已忽略的秘密文件，脚本不再含明文凭据，值未更换。
